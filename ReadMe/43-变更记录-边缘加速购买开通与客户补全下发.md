# 变更记录 — 边缘加速购买开通与客户补全下发

**日期**：2026-08-30  
**范围**：ISPmanager 自动开通 / 门户协议配置 / ISPweb 我的服务  
**对应**：门户购买 → 支付/信誉值 → 自动开通预分配 → 客户补全 → 保存并下发 → POP 生效回写

---

## 问题

原先 `_provision_edge` 在付款后立刻要求工单上已有 GRE 本端/对端 IP，并马上把隧道推到节点。客户在 ISPweb 下单时通常还没有对端地址，自动开通会失败或把未完成隧道下到 POP。

带宽分配、隧道地址段、POP 管理 IP、业务 IP 的 `/32` 主机路由也没有按「先预占、再生效」拆开。

---

## 目标流程

```
ISPweb 选购边缘产品
    → 直付 / 信誉值支付（或零金额）
    → payment_fulfillment / auto_provision
    → POP.config_mode=auto 时进入自动开通
    → 创建服务工单 + 服务实例（开通中）
    → 资源管理 / 边缘加速 生成「待配置」记录
         · 按采购规格写带宽分配
         · 从该 POP 未分配业务 IP 中领取
         · 从隧道 IP 地址段领取 p2p 块（本端/对端占用）
         · 我司对接地址 = POP.mgmt_ip
    → 同步到门户「我的服务」
    → 客户在 管理 → 协议配置 看到待补全项与对端应配内容
    → 补全后「保存并下发」
    → ISPmanager 下发到对应 POP
    → 节点生效后回写：隧道已下发、实例激活、业务 IP 以 /32 主机路由下到隧道接口
```

Socks5、多实例、独立带宽、手动 POP 仍走人开交付，不走本链路。

---

## 实现要点

1. **开通只预分配，不推隧道**  
   GRE/WG 不再要求下单时填写对端 IP；实例保持 `provisioning`，边缘保持 `pending`。
2. **系统锁定字段**  
   本端 IP（POP 管理 IP）、隧道 IP/CIDR（地址段分配）客户不可改。
3. **客户补全**  
   GRE：远端公网 IP。WireGuard：对端公钥（及可选 Endpoint）。
4. **下发门槛**  
   协议未补全或 `_build_tunnel_spec` 不完整时跳过该条，避免空 remote 写入 netplan。
5. **生效回写**  
   `finalize_edge_after_push`：边缘改运行中、激活服务实例、业务 IP 一律 `/32` 下发。
